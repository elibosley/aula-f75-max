# Fast Bluetooth settings candidate

This extends the main MCU and the enrolled Mac helper. It does not change the supplier radio, Bluetooth descriptor, bonds or recovery code. The target is a fresh typical-settings read and a small verified Apply in 1–2 seconds. Hardware timing is not yet verified. Dense configurations and large edits may take longer.

The measured baseline was 18.331 seconds for five RPCs. Every request sent 80 LED output symbols. Four setup/cleanup calls consumed 13.146 seconds; the actual compressed snapshot reply was 167 bytes. The radio was physically observed forwarding output bits 3 and 4, in addition to the existing high three bits. The lowest three Num/Caps/Scroll output bits were restored.

The qualified fast carrier uses output bits 3–7. A reset symbol zero precedes start 27. Data symbols are 1–26. Each nibble advances the preceding symbol by 1–16 modulo 26. No fast symbol has the legacy top-three-bit start value 7, so an old legacy decoder cannot interpret a fast frame as a command after the reset. Every frame still has a CRC32. The lowest three LED state bits are retained. Replies still use only report 2 Constant byte 1, never Apple Fn byte 7 or a key field. Fast replies now have a proposed 8 ms floor and remain serialized behind UART acknowledgments. Physical testing of the earlier 2 ms candidate passed all sixteen zero-key-event probes, but its first fresh Read failed parity after 64 reply bytes. No Bluetooth Apply was attempted, RAM stayed byte-exact, and the fast path was disabled. A UART acknowledgment proves radio acceptance, not BLE delivery. The new pacing still requires physical qualification.

A fast frame is `[5, command, length, nonce32, offset16, body, CRC32]`, with length equal to six plus the body length. Command 9 freezes and returns compressed settings immediately. The offset is the decoded cursor. Its reply payload is protocol 1, capabilities 7, snapshot CRC32, consumed u16, then bounded PackBits tokens. Continuations retain the same nonce/session and frozen snapshot. The final window releases ownership. An interrupted snapshot times out or is released by the existing route/disconnect cleanup.

An optional one-byte Command 9 body of `2` requests snapshot codec 2. The reply's first payload byte then equals 2. It preserves the PackBits format except token `0x80`, unused by the original encoder, which is followed by a nonzero little-endian u16 zero-span length. The encoder uses that token only for zero runs longer than 256 bytes. Every decoded window remains bounded and covered by the complete snapshot identity and both embedded record CRCs. This removes repeated empty mapping/macro spans without caching settings or adding a dictionary/RAM buffer. On the captured physical configuration, the encoded snapshot shrinks from 150 to 105 bytes before framing. A helper advertises `fast_snapshot_codec: 2` only from an explicitly qualified device record; absent metadata selects codec 1. Older requests and clients retain codec 1 unchanged. An unknown codec is rejected before taking snapshot ownership.

Codec 2 is installed and physically verified: a fresh full Read took 3.138 seconds, a one-field RAM Apply with live CRC took 2.093 seconds, and restoration took 1.994 seconds. Both directions preserved settings and Save counters, with zero keyboard events during the tests. The native Mac app also displayed a successful three-second Bluetooth Read. A bounded no-command API test found that asynchronous output still averaged about 30 ms per report; it did not remove the transport bottleneck.

Candidate codec 3 XORs each byte of the frozen snapshot with an immutable public factory dictionary, then uses codec 2 compression. Its request body and response codec byte are 3. The dictionary SHA-256 is `5f65936ad3fcacab3b16b979090689748172e8c925b68919499e0c47b9e0f4fa`. It consists of a 176-byte prefix, 3052 zero bytes and a four-byte tail. The MCU stores only the 180 nonzero-region bytes in flash, with no new RAM buffer. The dictionary must remain fixed even if future factory defaults change. The decoder reconstructs all current bytes at each window's absolute offset and validates both records and the live snapshot CRC. This is dictionary compression of a fresh snapshot, not a cached settings read. The captured configuration encodes to 28 bytes before framing, compared with codec 2's 105. Physical codec 3 speed is not yet proven.

Command 10 is an atomic small edit. Offset 0 means RAM Apply; offset 1 explicitly requests Save. The body starts with the expected current snapshot CRC32, followed by ordered `[offset16, count8, changed bytes]` patches, within 48 total body bytes. Record CRC words cannot be patched. The firmware rebuilds both record CRCs, validates through the existing commit path, and waits for Apply or flash Save completion. Its response carries the terminal phase and a CRC from the live configuration. A stale baseline, malformed patch, failed Save or unknown result never causes a retry or another transport.

The dictionary candidate also accepts a six-byte Command 10 body: baseline CRC32, one core-field byte offset, and its new byte value. It is restricted to offsets 114–121 and 125–127. The existing record decoder still validates the resulting setting. Other positions are rejected. The host selects this format only with explicit `fast_patch_version: 2` qualification; other clients retain ordered patches. This removes four output symbols from common wheel, brightness and theme changes without changing commit or live-CRC verification.

The host uses the fast carrier only when its per-device zero-event qualification receipt explicitly has `fast_settings_version: 1` and `fast_capability_verified: true`. The latter is issued only after guarded installation and the new main MCU's USB health capability bit 6 is checked. Existing qualification files select the unchanged legacy protocol. An unrecognized fast response is an error, not a reason to retry on the old carrier. Old Info v3 and capability flags 7 are unchanged. Large edits that do not fit one atomic request are selected before transmission for the existing staged transaction.

A failed fast Read does not send a legacy End request as cleanup. The board's bounded session timeout releases it. The helper records request-send duration separately so hardware measurements can distinguish output latency from the reply stream.

After a new dictionary image is installed and its carrier passes the fresh sixteen-pattern test, its qualification may additionally state `fast_snapshot_codec_max: 3`. New helpers then advertise codec 3 and patch version 2. The original `fast_snapshot_codec: 2` field remains in the record so the already-installed older app continues using codec 2. The new app is built only after the candidate passes verification; its physical performance still needs measurement.

The faster path is not admitted by compilation alone. Required proof includes the linked ARM carrier, snapshot CRC, stale baseline, atomic RAM Apply, completed Save, held-key preservation, corrupt-frame rejection and route cancellation checks. Installation still needs fresh zero-key-event probes and physical timing/round-trip tests. A 1–2 second claim requires the latter.

## Home refinement

The companion Home screen removes its redundant mood text. A compact heart-and-speed badge appears below the desk only during typing, Flow or Zoom, and disappears when idle. Notification signs keep priority. Existing font, palette, contrast, light/dark themes and dirty-tile invalidation remain in use.
